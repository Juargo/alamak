# ADR-0010: CI/CD con GitHub Actions y la integración Git de Vercel

- **Estado:** Aceptado
- **Fecha:** 2026-10-27
- **Fase:** Validación y Producto
- **Requisitos:** RES-14, RES-15, RNF-18, RNF-26, D-10, D-16

> **Nota (2026-10-28):** lo que este ADR decide sobre Supabase está reemplazado por [ADR-0014](0014-neon-como-base-de-datos.md) (Neon), por falta de presupuesto. El resto sigue vigente.

## Contexto
- El repo es privado (`Juargo/alamak`) y está en el plan gratuito de GitHub: **2.000 minutos de Actions al mes** y **sin reglas de protección de rama** en repos privados.
- Los PR los generan agentes. La CI es la red de seguridad principal, porque la revisión humana es breve.
- Supabase Free no da respaldos descargables (ADR-0003).

## Decisión
### Flujo de trabajo
- *Trunk-based*: una rama corta por issue (`issue-<n>-slug`), PR a `main` y *squash merge*. Commits con Conventional Commits.
- **Regla:** no se fusiona un PR con la CI en rojo. Sin protección de rama, esto depende de la disciplina. Si se quiere que GitHub lo obligue: GitHub Pro (US$4 al mes) o hacer el repo público.

### CI: `.github/workflows/ci.yml`, en cada PR y en cada push a `main`
| Paso | Herramienta | Rompe el build si… |
|---|---|---|
| 1. Instalar | pnpm con caché | — |
| 2. Estático | `tsc --noEmit`, ESLint, Prettier `--check`, `dependency-cruiser` | Hay errores de tipos o de lint, o se rompe un límite entre módulos |
| 3. Unitarias | Vitest + cobertura | Falla un test o la cobertura del dominio baja del umbral (ADR-0012) |
| 4. Integración | `supabase start` → migraciones → `supabase test db` (pgTAP/RLS) → Vitest de integración | Falla un test, o hay una tabla sin RLS |
| 5. Build | `next build` | Falla el build |
| 6. E2E de humo | Playwright (solo los flujos Must) contra el build local | Falla un flujo crítico |
| 7. Seguridad | gitleaks, Semgrep CE, `pnpm audit --prod --audit-level high` | Aparece un secreto, un hallazgo alto o una vulnerabilidad alta o crítica |

- **Presupuesto de tiempo:** ≤ 10 min por ejecución, para caber en ~2.000 min al mes. Los jobs se cancelan si llega un commit nuevo a la misma rama (`concurrency`) y las Actions se fijan por SHA.
- Si el presupuesto se agota: E2E solo en `main` y Semgrep solo en los PR que tocan `src/`.

### CD
- **Web:** integración Git de Vercel. Un *preview* por PR (para revisarlo en el móvil) y producción automática al fusionar en `main`.
- **Migraciones de base:** workflow `migrate.yml` en cada push a `main` que ejecuta `supabase db push` contra producción, con secretos de Actions.
  - Como Vercel y Actions corren en paralelo, toda migración debe ser **compatible hacia atrás** (*expand/contract*, ADR-0005).
- **Reversión:**
  - Web: *Instant Rollback* de Vercel al despliegue anterior.
  - Base: siempre hacia adelante con una migración correctiva (no se usan migraciones *down*).

### Tareas programadas
| Tarea | Dónde | Frecuencia |
|---|---|---|
| Latido de Supabase Free | Vercel Cron → `/api/v1/jobs/latido` | Diaria |
| Respaldo: `pg_dump` por el *session pooler* (IPv4) → cifrado con `age` → *artifact* con `retention-days: 30` (D-10) | GitHub Actions `backup.yml` | Diaria |
| Prueba de restauración del respaldo en un Postgres efímero | GitHub Actions | Mensual |
| Actualización de dependencias (agrupadas) | Dependabot | Semanal |

La clave privada de `age` vive **fuera** de GitHub (gestor de contraseñas de Jorge); en el repo solo está la pública.

## Alternativas consideradas
| Alternativa | Por qué no |
|---|---|
| Solo los checks de Vercel, sin Actions | No corren los tests de base, RLS ni seguridad |
| GitLab CI | El backlog y el repo ya están en GitHub (D-16) |
| Ambientes de GitHub con aprobación manual | En repos privados requieren un plan pago |
| Migraciones *down* | En producción, revertir esquemas con datos es más riesgoso que avanzar |

## Consecuencias
- **Positivas:** cada PR llega probado (incluido el aislamiento entre usuarios); despliegue y reversión en minutos; respaldos propios gratis.
- **Negativas / costos:** sin protección de rama, la regla de no fusionar en rojo es disciplina; hay que vigilar los minutos de Actions; las migraciones exigen diseño compatible hacia atrás.
- **Revisar cuando:** se agoten los minutos con frecuencia, se pase a Supabase Pro (sus respaldos diarios reemplazan al propio) o se sume otra persona al repo.
